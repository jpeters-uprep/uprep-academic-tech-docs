# Part A — Platform & configuration

## A1. Fix the sidebar situation (P0)

**What's actually happening.** In `docusaurus.config.ts`:

```ts
docs: {
  routeBasePath: "/",
  // sidebarPath: "./sidebars.ts",   // ← commented out
},
```

With `sidebarPath` unset and no `sidebars.js` present, Docusaurus falls back to
a **fully autogenerated sidebar**. Confirmed empirically from the generated site
data: the live sidebar is named `defaultSidebar`, not the `tutorialSidebar`
defined in `sidebars.ts`.

Consequences:

- **`sidebars.ts` is orphaned and stale.** It references doc IDs that don't
  exist (`software-and-vr/adobe-create-cloud` — note the typo, `makers-tools`
  and `programs-teams-and-clubs` at the root rather than under `makers/`) and it
  omits `faculty/`, `tech-resources/`, and `it-support/` entirely. If you ever
  uncomment that line, **the build will fail immediately.**
- **`README.md` is wrong.** It tells a future maintainer (or a future you) that
  "adding a new `.mdx` file doesn't automatically add it to the nav; it has to
  be added to `sidebars.ts` too." The opposite is true today: files appear
  automatically and `sidebars.ts` is ignored.
- **Ordering is alphabetical-by-title**, which is why nav order looks arbitrary.

**Recommendation — commit to autogenerated sidebars.** For a solo maintainer
this is the lower-maintenance choice; you just need to take control of _labels
and order_, which autogeneration supports properly.

Do this:

1. **Delete `website/sidebars.ts`** (or keep it renamed `sidebars.ts.disabled`
   if you want the history; do not leave a file that looks live).
2. Add a **`_category_.json`** to every folder under `docs/`, e.g.
   `docs/faculty/schoology/_category_.json`:
   ```json
   {
     "label": "Schoology",
     "position": 1,
     "link": { "type": "doc", "id": "faculty/schoology/index" },
     "customProps": { "description": "LMS guidance for teachers" }
   }
   ```
   This replaces the need for `sidebar_position` sprinkled in page frontmatter
   and makes ordering visible at a glance in the file tree.
3. Add `sidebar_position` to page frontmatter only where order is _meaningful_
   (see the Resources walkthrough, §5.4).
4. **Rewrite the "sidebar" bullet in `README.md`** to describe autogeneration +
   `_category_.json`.

**Alternative (only if you want tighter editorial control):** uncomment
`sidebarPath` and rewrite `sidebars.ts` from scratch to match the real tree.
This gives you exact ordering and lets one page appear in two places, at the
cost of hand-editing the file on every new page. Given how often you add pages
(25+ commits since mid-July), I'd advise against it.

## A5. Fix the Prettier setup — it explains the inconsistent formatting (P1)

Two bugs mean **`.mdx` files are never formatted**:

1. `package.json` → `"format:md": "prettier --write \"**/*.md\""` — the glob
   matches `.md` only. Every content file in this repo is `.mdx`.
2. `.vscode/settings.json` sets `editor.defaultFormatter` under `"[markdown]"`
   only. VS Code treats `.mdx` as language ID `mdx`, so format-on-save doesn't
   fire either.

That's why `unsupported-software.mdx` is one 500-character line,
`vr-software.mdx` is unwrapped, and everything else is neatly wrapped at 80.
Fixes:

```json
"format:md": "prettier --write \"**/*.{md,mdx}\""
```

```json
"[mdx]": { "editor.defaultFormatter": "esbenp.prettier-vscode" }
```

Also: **upgrade Prettier from `^2.8.8` to `^3`** — Prettier 2 has known MDX v3
parsing gaps, and Docusaurus 3.10 uses MDX v3. And add `.mdx` to
`.prettierignore` exclusions only if you hit a component it mangles.

## A7. Make the site machine-readable for AI answering (P1)

This is audience #4 and it's currently unserved. Five changes, in order of
value:

1. **Add `llms.txt` and `llms-full.txt`** via `docusaurus-plugin-llms`. This
   gives an AI a single fetchable, structured dump of the whole site instead of
   crawling 60 HTML pages. This is the biggest single win for "use AI to answer
   questions."
2. **Add `description:` frontmatter to every page.** It feeds search snippets,
   link previews, and AI retrieval. Right now no page has one.
3. **Adopt ownership frontmatter site-wide.** `chromebook-access-control.mdx`
   already does this well but as _body text_
   (`Owner: Brian Johnson; Author: June Peters; Reviewers: ...`). Promote it to
   structured frontmatter on every page and render it in a small footer
   component:
   ```yaml
   owner: ILT # or: Academic Technology | IT | Registrar
   maintainer: June Peters
   last_reviewed: 2026-08-19
   audience: [faculty] # faculty | students | families | staff
   ```
   Why this matters for your email workflow: when an AI reads two pages that
   disagree, `owner` + `last_reviewed` is how it decides which one to trust.
   Without it, it will confidently quote whichever page it saw first.
4. **Add `tags:`** and enable the docs tags page, so "everything a parent needs"
   and "everything about the gradebook" become real, linkable views without
   restructuring folders.
5. **Enforce one-fact-one-place.** This is the discipline, not a plugin: every
   factual claim lives on exactly one page and every other mention links to it.
   See §6.1 for the four places you're currently violating this — each one is a
   future wrong answer.
6. **Flag policy documents as suggest-only for AI editing.** _(Added after
   initial review, at June's request.)_ A handful of pages are governance/policy
   documents — ILT- or IT-owned, or otherwise not June's to unilaterally rewrite
   — where an AI assistant should propose changes in conversation rather than
   edit the page directly. These carry an `ai_editing: suggest-only` frontmatter
   field plus an `ai_edit_note:` explaining the boundary in plain language:

   ```yaml
   ai_editing: suggest-only
   ai_edit_note: >-
     This is a policy document. Propose changes in conversation for a human to
     review and apply, rather than editing the body directly.
   ```

   The flagged pages:
   - `faculty/schoology/requirements.mdx` (Schoology Requirements — ILT-owned)
   - `tech-resources/privacy-and-coppa.mdx` (Privacy and COPPA — IT-owned)
   - `tech-resources/student-laptops/middle-school-chromebooks.mdx`
   - `tech-resources/student-laptops/upper-school-laptops.mdx`
   - `tech-resources/technology-use-guidelines.mdx`
   - `faculty/teacher-software/software-process.mdx`
   - `software-and-vr/fully-supported-software/index.mdx` — **partial lock**:
     the list of approved software itself is policy-controlled, but
     descriptions, formatting, and page layout may still be edited freely. The
     `ai_edit_note` on this page spells out that distinction rather than using a
     different field name.

   This is a convention for AI tooling to respect, not a Docusaurus or
   filesystem-level permission — it doesn't stop a human editing the file, and
   it doesn't stop a careless AI that doesn't check frontmatter first. Treat it
   as a clearly-posted sign, not a lock.

**Optional but powerful:** Docusaurus supports `unlisted: true` (page builds and
is reachable by URL, but is excluded from sidebar, search, and sitemap).
Consider an `internal/` folder of unlisted "answer bank" pages — canned language
for the emails you answer most, escalation paths, what-to-say-when. It becomes
part of the AI's context without being part of the public site.

# Part B — Information architecture

## B1. The core problem

The site is organized by **system** (Schoology, Veracross, Software, Makers) and
partly by **role** (Faculty), with one catch-all (`tech-resources`). Because the
sidebar is autogenerated and sorted alphabetically by title, the top level
renders like this:

```
Home
Accessibility            ← a single leaf page, sorted first
Faculty Resources
IT Support               ← one page, a pointer offsite
Makers
Software and VR
Technology Resources     ← laptops, privacy, policies, family Schoology — sorted LAST
```

Specific failures this produces:

- **A parent** looking for the Chromebook they must buy has to guess that
  "Technology Resources" (bottom of the list) is the right door, not "IT
  Support."
- **A student** has no entry point at all. Nothing on the site is addressed to
  them, though plenty is _for_ them (VR software, Makers tools, printing,
  passwords, accessibility).
- **Schoology is split across two unconnected sections**: `faculty/schoology/*`
  (teachers) and `tech-resources/schoology-overview` (families). Neither links
  to the other, and there's no student-facing Schoology page at all.
- **"Accessibility"** is a top-level leaf, so it reads as more important than
  laptops or Schoology.
- **"Software and VR"** bundles a major category with a minor one in the label.
  VR is one page of five.
- **"IT Support"** is a section containing exactly one page whose content is "go
  to a different website."

## B3. Migration safety

A restructure at this scale breaks every existing URL — including links you've
already pasted into emails, Schoology courses, and the Veracross portal.
**Install `@docusaurus/plugin-client-redirects` before you move anything** and
add a redirect for every moved path. This is non-negotiable given how much of
this site is linked from elsewhere.

If you'd rather not do a full restructure, the **minimum-churn version**
captures most of the value:

1. Fix `sidebar_position` on every section index so the top level reads in a
   sensible order (Faculty, Families/Tech Resources, Software, Makers,
   Accessibility, IT Support).
2. Rename `tech-resources` → **"For Students & Families"** as a label (via
   `_category_.json`, no file moves, no broken links).
3. Turn `home.mdx` into a three-card audience router.
4. Cross-link the two Schoology sections in both directions.
5. Demote `accessibility.mdx` under the audience it serves.

That's an afternoon. The full restructure is 1–2 days including redirects.

### Problem 1 — Three pages answer "how should I use Schoology?"

| Topic                | `requirements`          | `best-practices`  | `student-centered-courses`                |
| -------------------- | ----------------------- | ----------------- | ----------------------------------------- |
| Syllabus required    | ✅ "must have"          | —                 | ✅ "Please upload" (softer — contradicts) |

| Material types       | —                       | —                 | ✅                                        |

`student-centered-courses.mdx` is a **migration artifact** — its opening line is
"Getting Started with Schoology" and its second section is "UPrep Community
Expectations for Schoology," i.e. an older version of `requirements.mdx`. Three

version having the vaguest title. The frontmatter title ("Student Centered
Courses") doesn't describe the content at all, so nobody can tell from the
sidebar which page is authoritative.

**Worst case in practice:** a teacher reads "you can use whatever grade-keeping
system you prefer" (`student-centered-courses`) and never sees "Schoology must
still be used to record grades" (`requirements`, Middle School). An AI reading
both will give whichever answer it retrieved.

### Problem 2 — `best-practices.mdx` is a 10 KB monolith

It contains nine distinct topics with no internal navigation, and its own

restructure you flagged. It also carries three artifacts:

- A **stray page footer** at the bottom:
  `University Prep Home - Veracross Portal - Schoology` /
  `Site Managed by June Peters, Academic Tech PM` — leftover from the old
  Schoology-hosted training site. This belongs in the site footer (where it
  already is), not in page content.
- **"Feel free to print this page as a checklist"** — but the page isn't a
  checklist. (Good idea though; see C3, new page 2.)
- A section-internal "see below" that survives only because the sections are on

  it.

### Problem 3 — The Resources walkthrough is out of order and its navigation is broken

The intended sequence is **Working in Resources → Saving to Resources → Adding
Resources to a Course**. Because autogeneration sorts alphabetically by title,
the sidebar renders:

> Adding Resources to a Course · Best Practices · Course Headers · Rubrics ·
> Saving to Resources · Student Centered Courses · Working in Resources

So the walkthrough is served backwards and interleaved with unrelated pages. And
`working-in-resources.mdx` ends with:

> Click "Next" above to go to Adding Resources to Courses

**That instruction is broken.** "Working in Resources" sorts _last_ in the
folder, so Docusaurus's Next link points somewhere else entirely. There is also
no "Next" button "above" — Docusaurus renders pagination at the bottom of the
page. This is a concrete, user-visible navigation failure.

### Problem 4 — The section index does no work

`faculty/schoology/index.mdx` is a heading, an external link, and

## F2. Titles and H1s — pick one convention

Docusaurus renders the frontmatter `title` as the H1. A separate `#` heading
creates **two** headings. Current inconsistencies:

- `accessibility.mdx` — title "Accessibility" + H1 "Accessibility Tools for
  Students and Faculty"

- `ppe.mdx` — title + a longer H1
- `chromebook-access-control.mdx` — title + an **identical** H1 (renders the
  heading twice)
- 7 pages — H1 only, no frontmatter

**Rule:** frontmatter `title` only; never an `#` H1 in the body. Start pages at
`##`.

## F3. Links — root-absolute, or file-relative to `.mdx`

The site currently mixes three styles, including `](../.)`. URL-relative links
depend on `trailingSlash: true` staying true and on pages never moving. Two safe
options:

- **`/faculty/schoology/requirements`** — root-absolute, validated at build by
  `onBrokenLinks: "throw"`.
- **`./requirements.mdx`** — file-relative _with the extension_, which
  Docusaurus resolves and validates against the file, so it survives URL
  changes.

Pick one (I'd use root-absolute for cross-section links and `./file.mdx` within
a folder) and convert the 16 files currently using bare relative paths.

## F4. FAQ pages — keep the pattern you already have

tweaks: make titles consistently interrogative ("Where do I find 3D models?" not
"Where to find models?"), and add a `## Related` section (as
`family-link-school-account` already does) so each FAQ becomes a hub rather than
a dead end.
