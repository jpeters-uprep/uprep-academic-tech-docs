# Agent instructions

Operating instructions for AI coding agents working in this repo. For content
standards (frontmatter, headings, links, FAQ structure, naming) see
[CONTRIBUTING.md](CONTRIBUTING.md) — don't duplicate those rules here, just
follow them.

## Repo layout

- The actual Docusaurus project lives in `website/`, not the repo root. Run all
  `npm` commands from inside `website/`.
- Content is `.mdx` under `website/docs/`. The sidebar is fully autogenerated
  from that folder tree — there is no `sidebars.ts`. A folder's label/order
  comes from its `_category_.json`; a single page's order comes from its own
  `sidebar_position` frontmatter field.
- `design-docs/SITE-REVIEW-PLAN.md` is the project's working plan and decision
  log for the ongoing site review (not published to the site). If you're picking
  up review/cleanup work, read it first — it records what's already been
  decided, corrected, reverted, or deliberately held, including cases where an
  earlier pass (mine or the plan's own) turned out to be wrong. Update it as you
  go, in the same style: log what changed and why, don't just silently mark
  things done.

## Commands (run from `website/`)

- `npm run typecheck` — type-checks the config files.
- `npm run build` — full production build. Docusaurus is configured with
  `onBrokenLinks: "throw"` and `onBrokenAnchors: "throw"`, so a bad link or
  anchor fails the build. **Build before you commit, not after.**
- `npm run format:md` — Prettier over all `.md`/`.mdx` files, repo-wide.
- Clean up build output after verifying: `rm -rf build .docusaurus`.

## Before finishing any content change

- [ ] `npm run build` succeeds.
- [ ] `npm run typecheck` passes.
- [ ] `npm run format:md` produces no diff — **except** on
      `ai_editing: suggest-only` pages (see below), which should be left exactly
      as their human author formatted them, even if that means an unwrapped or
      oddly-wrapped line.
- [ ] Any moved or renamed page has a redirect entry, and you've confirmed at
      least one old URL still resolves.
- [ ] No page body starts with a duplicate `#` heading (title already renders as
      the H1 — see CONTRIBUTING.md).

## `ai_editing: suggest-only` pages

**Read a file's frontmatter before editing its body.** If it has
`ai_editing: suggest-only`, don't edit the body yourself — not even
formatting-only changes like re-wrapping a line. Propose the exact change in
conversation instead and let a human apply it. This has bitten this project
before: a repo-wide `prettier --write` once reflowed a suggest-only page's
paragraph as a side effect, which is exactly the kind of body edit the
convention exists to prevent, even though no wording changed.

`ai_edit_note` in that page's frontmatter explains why it's restricted and
sometimes narrows the restriction (e.g. "formatting and layout may still be
edited freely" on a page where only the _list contents_ are policy-controlled) —
read it, don't assume the strictest interpretation applies everywhere.

## Git and PR conventions

- Don't `git commit` or `git push` without being explicitly asked, even after
  finishing a chunk of work — surface what changed and wait. This project's
  owner regularly wants to review and hand-edit a diff before it's committed.
- `git reset HEAD~1` (not `--hard`) is the standard way to "uncommit" while
  keeping everything as working-tree edits, when asked to let a human review or
  edit before committing.
- Attribute a commit to the AI tool with a `Co-Authored-By:` trailer, _except_
  when the commit is genuinely a human's own manual edit (they typed it directly
  into a file, including into a suggest-only page) — in that case use
  `git commit --author` with their name/email and omit the trailer.
- One branch per logical chunk of plan work (e.g. `site-review-part-e`), one PR
  per branch. If a branch's PR has already merged, cut the next branch from the
  now-updated default branch rather than continuing on the merged one.
